Vaadin Signals

Reactive UIs for Java

signal · computed · effect

We all know signals from the JS world: SolidJS, Preact, Angular.

Now Vaadin brings the same model to server-side Java.

Today we'll see why this matters and what's different.

The tangle

· State management can get out of control.
· A simple form with a few listeners can become a tangled mess of components updating each other: you need a notepad just to keep track of what updates what.

Listener chains

Each field manually wires a Listener to everything that depends on its value.

Forgotten subscriptions

Components drift out of sync. Bugs that only show up in specific click orders.

Imperative updates

You spend more time orchestrating "who tells whom" than writing logic.

Every dev who has built a non-trivial form has lived this.

The video calls it a "notepad to keep track of what updates what".

That's exactly the problem reactive systems were designed to kill.

1

Why signals?

The frontend world has spent 15 years answering this question.

Let's recap quickly because Vaadin inherits all of that thinking.

Imperative vs Reactive

Imperative: "tell each thing"


nameInput.on('input', e => {
  greeting.text = 'Hello ' + e.value;
  saveBtn.enabled = e.value.length > 0;
  status.text = `${e.value.length} chars`;
});

Reactive: "describe relationships"


const name = signal('');
const greeting = computed(() => 'Hello ' + name.value);
const canSave  = computed(() => name.value.length > 0);
const status   = computed(() => `${name.value.length} chars`);

Same behaviour.
The reactive version doesn't tell anyone anything: it just declares dependencies.

The imperative version works, but each new field doubles the listener wiring.

The reactive version doesn't grow that way: each piece of state declares what it depends on.

The framework figures out the update order.

Push, Pull, Push-Pull

Pull
(React, Preact, Vue 2)

Something changed somewhere. Rerender the whole subtree and diff. Coarse. Works. Wastes CPU.

Push
(Knockout)

Tell every observer immediately. Fast but can update the same thing multiple times in one tick.

Push-Pull
(Signals)

Mark dirty on write (push), recompute only what's read (pull). Fine-grained. Glitch-free.

Signals are not new: they are the model that finally made fine-grained reactivity simple.

Three models.

Pull is React: rerender and diff.

Push is Knockout-style observables: any change fires every subscriber.

Push-pull is what SolidJS popularised and Preact/Angular/Vaadin all adopted. Best of both worlds.

A 15-year overnight success

Signals are now backed by authors from Angular, Solid, Vue, Svelte, Preact and Qwik.

The signal idea is older than React. It went dormant during the virtual-DOM era and came back stronger.

TC39 is the ECMA committee that defines the official JavaScript standard.

Proposals go through 4 stages: 1 (idea accepted), 2 (draft), 3 (spec ready), 4 (in the language).

Signals reaching stage 1 in 2024 means industry consensus: the proposal is backed by authors from Angular, Solid, Vue, Svelte, Preact and Qwik.

Vaadin 25.1 brings it to Java, and its API is aligned with that proposal.

· Signals provide a language to describe state synchronization independent of any side effect.

: TC39 Signals proposal

This is the key insight.

Signals separate WHAT depends on what from WHEN and HOW to update.

The framework owns the WHEN. You only describe the WHAT.

2

Three primitives

signal   computed   effect

Three building blocks. That's it.

Signal, computed, effect.

Every signals library is some flavour of these three.

signal: a reactive value

Preact / JS


import { signal } from '@preact/signals';

const count = signal(0);

console.log(count.value);  // read
count.value = 1;           // write

Vaadin / Java


import com.vaadin.signals.ValueSignal;

ValueSignal<Integer> count = new ValueSignal<>(0);

count.value();      // read
count.value(1);     // write

One reactive cell.
Read it, write it, subscribe to changes.

A signal is a box around a value.

The box notifies anyone listening when the value changes.

That's the whole API surface for the first primitive.

computed: derived state

Preact / JS


const first = signal('Ada');
const last  = signal('Lovelace');

const full = computed(() =>
  first.value + ' ' + last.value
);

Vaadin / Java


ValueSignal<String> first = new ValueSignal<>("Ada");
ValueSignal<String> last  = new ValueSignal<>("Lovelace");

Signal<String> full = Signal.computed(() ->
  first.value() + " " + last.value()
);

Like an Excel formula: recalculates only when its inputs change.
Lazy.
Cached.

Computed is the Excel formula.

It tracks which signals it reads, and re-evaluates only when those change.

And only when someone actually asks for its value.

Lazy and memoised.

effect: the outside world

Preact / JS


effect(() => {
  document.title =
    `Hello ${full.value}`;
});

Vaadin / Java


Signal.effect(() -> {
  log.info("Name is now {}",
    full.value());
});

The bridge from reactive data to the imperative world: DOM, logs, network, the UI.

Effects are where reactivity meets reality.

You read signals, you do a side effect (update the DOM, call an API, log).

When any signal you read changes, the effect re-runs.

Vaadin scopes effects to the component lifecycle automatically.

Three primitives, one flow

Walk through the steps with the Next button.

Show signal -> computed -> effect once, then click the increment and watch the packet propagate.

Last step: glitch-free guarantee.

Emphasise: one push, each subscriber runs once.

Glitch-free, guaranteed


const a = signal(1);
const b = computed(() => a.value * 2);    // depends on a
const c = computed(() => a.value + b.value); // depends on a AND b

effect(() => render(c.value));    // runs ONCE per change to a

Classic observable

a changes → effect runs twice:
once via a, once via b.

Signals

Effect runs exactly once.
The framework topologically sorts the dependency graph.

This is what "glitch-free" means and why naive observable libraries get it wrong.

When 'a' changes, 'b' and 'c' both depend on it. A naive system would fire the effect twice.

Signals run it once, with the correct final value.

This matters at scale.

3

Vaadin's solution

Same model. Server-side. Multi-user.

Everything we've seen so far runs in the browser.

Vaadin's contribution: put the same primitives on the JVM, and let them sync across users automatically.

Signals, but on the JVM

Thread-safe

Reads and writes are atomic. Background tasks, REST callbacks, scheduled jobs: all safe.

Shared by default

One ListSignal<Order> on the server can drive every connected browser session.

Transactional

Multiple writes in one block: subscribers see the final state, not the intermediate flicker.

Three things JS signals don't give you.

Threads, sharing across users, and atomic batches.

That's what makes signals on the JVM more than just a port.

Hello world with Vaadin Signals

Classic Flow


@Route("hello")
public class HelloView extends VerticalLayout {

    public HelloView() {
        TextField input = new TextField("Your name");
        Span greeting = new Span("Type your name...");

        input.setValueChangeMode(ValueChangeMode.EAGER);
        input.addValueChangeListener(e -> {
            String v = e.getValue();
            greeting.setText(v.isEmpty()
                ? "Type your name..."
                : "Hello, " + v + "!");
        });

        add(input, greeting);
    }
}

With Vaadin Signals


@Route("hello")
public class HelloView extends VerticalLayout {

    public HelloView() {
        var name = new ValueSignal<>("");

        add(new TextField("Your name", name));

        add(new Span(Signal.computed(() ->
            name.value().isEmpty()
                ? "Type your name..."
                : "Hello, " + name.value() + "!")));
    }
}

No listeners.
No addValueChangeListener.
The Span re-renders itself.

A full Vaadin hello-world with signals.

Notice: no addValueChangeListener anywhere.

The bindText call creates a subscription automatically and tears it down when the component is detached.

That's the whole pitch.

The binding API

component.bindValue(signal, signal::set) Two-way bind a field's value to a signal.
component.bindText(signal) Set textContent from a signal or computed.
component.bindVisible(signal) Show or hide based on a boolean signal.
component.bindEnabled(signal) Enable or disable from a boolean signal.
grid.bindItems(listSignal) Grid rows track a ListSignal<T> automatically.
Signal.effect(...) Scoped to the current component. Cleaned up on detach.

The binding API is the high-level facade.

Most of the time you'll never write a raw effect: you'll bind a component property to a signal and Vaadin handles the rest.

on the JVM

// Shared application-scope signal
@Component
class OrderRegistry {
    final ListSignal<Order> orders = new ListSignal<>();
}

// Every view that binds to this list sees the same data, live.
grid.bindItems(orderRegistry.orders);

A new Order from any browser updates the Grid in every connected session.

This is the killer demo.

One ListSignal on the server. Three distinct users, each in their own browser, see the same data live.

No WebSocket code, no event bus, no Redis pub-sub. The framework handles propagation.

Try doing this with React + REST. You'd need a backend pub-sub, a WS endpoint, optimistic updates...

Before & after

Listeners (~26 LOC)


@Route("signup")
public class SignupView extends VerticalLayout {

  public SignupView() {
    TextField name  = new TextField("Name");
    TextField email = new TextField("Email");
    Span status = new Span();

    name.addValueChangeListener(e ->
      recalcStatus(name, email, status));
    email.addValueChangeListener(e ->
      recalcStatus(name, email, status));

    add(name, email, status);
  }

  void recalcStatus(TextField name, TextField email, Span status) {
    if (name.isEmpty()) {
      status.setText("Name?");
    } else if (email.isEmpty()) {
      status.setText("Email?");
    } else {
      status.setText("Looks good");
    }
  }
}

With signals (~15 LOC)


@Route("signup")
public class SignupView extends VerticalLayout {

  public SignupView() {
    var name  = new ValueSignal<>("");
    var email = new ValueSignal<>("");

    add(new TextField("Name", name));
    add(new TextField("Email", email));

    add(new Span(Signal.computed(() ->
      name.value().isEmpty()  ? "Name?"  :
      email.value().isEmpty() ? "Email?" :
                                "Looks good")));
  }
}

Same feature. 75% less code.

And the "after" version has no risk of forgetting a listener, no risk of stale state.

The dependency graph is described, not orchestrated.
