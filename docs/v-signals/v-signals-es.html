Vaadin Signals

UIs reactivas para Java

signal · computed · effect

Todos conocemos signals del mundo JavaScript: SolidJS, Preact, Angular.

Ahora Vaadin trae el mismo modelo a Java en el servidor.

Hoy vemos por qué importa y qué cambia.

El enredo

· El manejo del estado se nos va de las manos.
· Un simple formulario con unos pocos listeners se convierte en una maraña de componentes actualizándose entre sí.
· Necesitas una libreta para apuntar qué actualiza qué.

Cadenas de listeners

Cada campo conecta a mano un Listener con todo lo que dependa de su valor.

Suscripciones olvidadas

Los componentes se desincronizan. Bugs que sólo aparecen con un orden de clicks concreto.

Actualizaciones imperativas

Pasas más tiempo orquestando "quién avisa a quién" que escribiendo lógica.

Todo desarrollador que haya hecho un formulario no trivial ha vivido esto.

El vídeo lo llama "una libreta para saber qué actualiza qué".

Es exactamente el problema que los sistemas reactivos quieren matar.

¿Por qué signals?

El mundo frontend lleva 15 años contestando esta pregunta.

Repasemos rápido, porque Vaadin hereda toda esa reflexión.

Imperativo vs Reactivo

Imperativo: "dile a cada cosa"


nameInput.on('input', e => {
  greeting.text = 'Hola ' + e.value;
  saveBtn.enabled = e.value.length > 0;
  status.text = `${e.value.length} caracteres`;
});

Reactivo: "describe relaciones"


const name = signal('');
const greeting = computed(() => 'Hola ' + name.value);
const canSave  = computed(() => name.value.length > 0);
const status   = computed(() => `${name.value.length} caracteres`);

Mismo comportamiento.
La versión reactiva no le dice nada a nadie: sólo declara dependencias.

La versión imperativa funciona, pero cada campo nuevo duplica el cableado.

La reactiva no crece así: cada pieza declara de qué depende y el framework decide el orden de actualización.

Push, Pull, Push-Pull

Pull
(React, Preact, Vue 2)

Algo cambió. Re-renderiza el árbol entero y haz diff. Granularidad gruesa. Funciona. Desperdicia CPU.

Push
(Knockout)

Avisa a todos los observadores ya. Rápido, pero puede actualizar la misma cosa varias veces en un tick.

Push-Pull
(Signals)

Marca como sucio al escribir (push), recalcula sólo lo que se lee (pull). Granularidad fina. Sin glitches.

Los signals no son nuevos: son el modelo que por fin hizo simple la reactividad fina.

Tres modelos.

Pull es React: re-renderiza y haz diff.

Push es Knockout: cualquier cambio dispara todos los suscriptores.

Push-pull lo popularizó SolidJS y lo siguieron Preact, Angular y ahora Vaadin. Lo mejor de los dos mundos.

Tres primitivas

signal   computed   effect

Tres bloques de construcción. Eso es todo.

Signal, computed, effect.

Cada librería de signals es una variación sobre estos tres.

signal: un valor reactivo

Preact / JS


import { signal } from '@preact/signals';

const count = signal(0);

console.log(count.value);  // leer
count.value = 1;           // escribir

Vaadin / Java


import com.vaadin.signals.ValueSignal;

ValueSignal<Integer> count = new ValueSignal<>(0);

count.value();      // leer
count.value(1);     // escribir

Una celda reactiva.
Léela, escríbela, suscríbete a sus cambios.

Una signal es una caja que envuelve un valor.

La caja avisa a quien esté escuchando cuando el valor cambia.

Toda la superficie de la API de la primera primitiva.

computed: estado derivado

Preact / JS


const first = signal('Ada');
const last  = signal('Lovelace');

const full = computed(() =>
  first.value + ' ' + last.value
);

Vaadin / Java


ValueSignal<String> first = new ValueSignal<>("Ada");
ValueSignal<String> last  = new ValueSignal<>("Lovelace");

Signal<String> full = Signal.computed(() ->
  first.value() + " " + last.value()
);

Como una fórmula de Excel: se recalcula sólo cuando cambian sus entradas.
Perezosa.
Cacheada.

Computed es la fórmula de Excel.

Sabe qué signals lee, y vuelve a evaluarse sólo cuando esas cambian.

Y sólo cuando alguien pregunta su valor.

Perezosa y memoizada.

effect: el mundo exterior

Preact / JS


effect(() => {
  document.title =
    `Hola ${full.value}`;
});

Vaadin / Java


Signal.effect(() -> {
  log.info("Nombre actual: {}",
    full.value());
});

El puente entre los datos reactivos y el mundo imperativo: DOM, logs, red, la UI.

Los effects son donde la reactividad toca la realidad.

Lees signals, haces un side effect (actualizar el DOM, llamar a una API, loguear).

Cuando cualquier signal que leíste cambia, el effect se vuelve a ejecutar.

Vaadin lo limita al ciclo de vida del componente automáticamente.

Tres primitivas, un flujo

Recorre los pasos con el botón Next.

Muestra signal -> computed -> effect una vez, luego haz click en el +1 y mira cómo viaja el paquete.

Último paso: la garantía glitch-free.

Recalca: un push, cada suscriptor corre una vez.

Sin glitches, garantizado


const a = signal(1);
const b = computed(() => a.value * 2);    // depende de a
const c = computed(() => a.value + b.value); // depende de a Y b

effect(() => render(c.value));    // corre UNA vez por cambio en a

Observable clásico

Cambia a → el effect corre dos veces:
una por a, otra por b.

Signals

El effect corre exactamente una vez.
El framework ordena topológicamente el grafo.

Esto es lo que significa "glitch-free" y por qué las librerías de observables ingenuas fallan.

Cuando 'a' cambia, 'b' y 'c' dependen de ella. Un sistema ingenuo dispararía el effect dos veces.

Signals lo corre una sola vez, con el valor final correcto.

Importa a escala.

3

La solución de Vaadin

Mismo modelo. En el servidor. Multi-usuario.

Todo lo que hemos visto hasta ahora corre en el navegador.

La aportación de Vaadin: poner las mismas primitivas en la JVM y dejar que sincronicen entre usuarios automáticamente.

Signals, pero en la JVM

Thread-safe

Lecturas y escrituras atómicas. Tareas en background, callbacks REST, jobs programados: todos seguros.

Compartidos por defecto

Un ListSignal<Order> en el servidor puede alimentar a cada sesión conectada.

Transaccionales

Varias escrituras en un bloque: los suscriptores ven el estado final, no el parpadeo intermedio.

Tres cosas que los signals de JS no te dan.

Hilos, compartir entre usuarios y batches atómicos.

Eso es lo que hace que signals en la JVM sea más que un port.

El Hola Mundo con Vaadin Signals

Flow clásico


@Route("hello")
public class HelloView extends VerticalLayout {

    public HelloView() {
        TextField input = new TextField("Tu nombre");
        Span greeting = new Span("Escribe tu nombre...");

        input.setValueChangeMode(ValueChangeMode.EAGER);
        input.addValueChangeListener(e -> {
            String v = e.getValue();
            greeting.setText(v.isEmpty()
                ? "Escribe tu nombre..."
                : "¡Hola, " + v + "!");
        });

        add(input, greeting);
    }
}

Con Vaadin Signals


@Route("hello")
public class HelloView extends VerticalLayout {

    public HelloView() {
        var name = new ValueSignal<>("");

        add(new TextField("Tu nombre", name));

        add(new Span(Signal.computed(() ->
            name.value().isEmpty()
                ? "Escribe tu nombre..."
                : "¡Hola, " + name.value() + "!")));
    }
}

Sin listeners.
Sin addValueChangeListener.
El Span se re-renderiza solo.

Un hello-world completo de Vaadin con signals.

Fíjate: no hay ningún addValueChangeListener.

La llamada a bindText crea la suscripción automáticamente y la desmonta cuando el componente se detacha.

Ése es todo el argumento.

La API de bindings

component.bindValue(signal, signal::set) Bind bidireccional del valor de un campo a una signal.
component.bindText(signal) Pone el textContent desde una signal o computed.
component.bindVisible(signal) Muestra u oculta según una signal booleana.
component.bindEnabled(signal) Activa o desactiva desde una signal booleana.
grid.bindItems(listSignal) Las filas del Grid siguen una ListSignal<T> automáticamente.
Signal.effect(...) Ligado al componente actual. Limpieza automática al detach.

La API de bindings es la fachada de alto nivel.

La mayor parte del tiempo no escribirás un effect a mano: bindeas una propiedad del componente a una signal y Vaadin se ocupa del resto.

Ésta es la demo asesina.

Sin código WebSocket, sin event bus, sin Redis pub-sub. El framework propaga.

Intenta hacer esto con React y REST: necesitarías un pub-sub en el backend, un endpoint WS, optimistic updates...

Antes y después

Listeners (~26 líneas)


@Route("signup")
public class SignupView extends VerticalLayout {

  public SignupView() {
    TextField name  = new TextField("Nombre");
    TextField email = new TextField("Email");
    Span status = new Span();

    name.addValueChangeListener(e ->
      recalcStatus(name, email, status));
    email.addValueChangeListener(e ->
      recalcStatus(name, email, status));

    add(name, email, status);
  }

  void recalcStatus(TextField name, TextField email, Span status) {
    if (name.isEmpty()) {
      status.setText("¿Nombre?");
    } else if (email.isEmpty()) {
      status.setText("¿Email?");
    } else {
      status.setText("Todo en orden");
    }
  }
}

Con signals (~15 líneas)


@Route("signup")
public class SignupView extends VerticalLayout {

  public SignupView() {
    var name  = new ValueSignal<>("");
    var email = new ValueSignal<>("");

    add(new TextField("Nombre", name));
    add(new TextField("Email", email));

    add(new Span(Signal.computed(() ->
      name.value().isEmpty()  ? "¿Nombre?" :
      email.value().isEmpty() ? "¿Email?"  :
                                "Todo en orden")));
  }
}

Misma funcionalidad. 75% menos código.

Y la versión "después" no tiene riesgo de olvidar un listener, ni riesgo de estado obsoleto.

El grafo de dependencias se describe, no se orquesta.
